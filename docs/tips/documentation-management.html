Documentation management

1. Summary

  • Plans live under docs/plans/, in a folder that says what state they are in: active, implemented, archived or deferred.
  • A plan file is named <yyyy-mm-dd>-n<index>-<plan name>, with no spaces or special characters. Plans named before the four-digit year keep their yy-mm-dd names.
  • How a document looks and is laid out comes from the HTML documentation guideline.
  • The agent does not test its work live. The operator tests by hand.
  • CLAUDE.md and AGENTS.md mirror each other.

2. Plan folders

FolderHolds
docs/plans/Active plans: being written, or being worked from.
docs/plans/implemented/Completed plans. A plan moves here once it has shipped.
docs/plans/archived/Plans folded into a later plan that implements them as part of a whole. Kept for their reasoning, not worked from directly.
docs/plans/deferred/Plans set aside for development in the far future.

Moving a plan between folders does not change its filename.

3. Plan filenames

<yyyy-mm-dd>-n<index>-<plan name>.html
PartMeaning
<yyyy-mm-dd>The date the plan was created, not the date it was implemented or moved, with a four-digit year. Older plans named yy-mm-dd keep their names; they are not renamed.
n<index>1-based index of the plan among those created the same day (n1, n2, n3), so same-day plans don't collide.
<plan name>A short description of the plan, in lowercase words joined by hyphens.

Example:

2026-09-23-n1-sidebar-reorder-and-run-panel-strategy-list.html

3.1 Why no special characters

Browsers mangle spaces, # and other special characters in a URL. A space becomes %20, and everything after a # is read as a fragment, so the file does not open. Use only lowercase letters, digits and hyphens, plus the dot before the extension.

3.2 Naming a new plan

  1. Take today's date as yyyy-mm-dd.
  2. Look at the existing filenames for that date, in every plan folder and in both forms (yyyy-mm-dd and the older yy-mm-dd), and pick the next unused index.
  3. Add the plan name and the extension (.html or .md).

4. Formatting

Formatting is taken from the HTML documentation guideline (tips/html-documentation-guideline.html, next to this file). Read it before writing a document. In brief, it asks for:

  • A brief summary as the first section.
  • A table of contents at the side that follows the scrolling and marks the section being read. Every heading it links to has an id.
  • Visible section and step numbers, in the headings, in the table of contents and on the steps of any procedure, so a place can be referred to by number ("§3.2", "step 4").
  • A dark page with a light mode toggle at the top.
  • Demos, animations and diagrams when the user asks for them, written into the document itself.
  • A demo that needs more room goes wide and keeps its text and element sizes. It is not shrunk to fit the text column.

The guideline is the source. Where this list and the guideline differ, follow the guideline.

Documents are written as files in the repository. They are not published anywhere else.

5. No live testing

The agent does not test its work live. The operator tests the work by hand, and live testing by the agent costs tokens for a check that is going to be done anyway.

  • Don't start the app, drive it in a browser or take screenshots to confirm a change.
  • Don't open a document in a browser to check how it renders.
  • Checks at the level of the code are fine: reading the code back, a syntax check, a linter, existing unit tests.
  • In the final message, say what was checked and what was left for the operator to test.

6. Agent instruction files

  • CLAUDE.md and AGENTS.md hold the same guidance and must mirror each other.
  • A change to one is made to the other in the same change.
  • If they fall out of sync, the one edited most recently is authoritative and is copied over the other.
