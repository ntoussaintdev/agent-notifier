HTML documentation guideline

1. Summary

  • The first section of a document is a brief summary.
  • A table of contents sits at the side and follows the scrolling.
  • Sections and steps carry visible numbers, so a place in the document can be referred to by number.
  • The page is dark, with a light mode toggle at the top.
  • Demos, animations and diagrams are included when the user asks for them.
  • A demo goes wide when it needs the room, and stays wide on a small screen.

2. Table of contents

  • It sits at the side of the page and stays in view while the page scrolls.
  • It lists the sections and marks the one being read.
  • Every section heading it links to has an id.
nav.doc-toc { position: sticky; top: 24px; align-self: start; }
const links = Array.from(document.querySelectorAll('nav.doc-toc a'));
const byId = new Map(links.map((a) => [a.getAttribute('href').slice(1), a]));
const io = new IntersectionObserver((entries) => {
  entries.forEach((e) => {
    if (!e.isIntersecting) return;
    links.forEach((l) => l.classList.toggle('is-current', l === byId.get(e.target.id)));
  });
}, { rootMargin: '-15% 0px -75% 0px' });
byId.forEach((_, id) => io.observe(document.getElementById(id)));

3. Section and step numbers

Show section and step numbers in the text itself, so a place in the document can be referred to by number ("§3.2", "step 4").

  • Number the headings (1., 1.1, 2.) and put the same numbers in the table of contents.
  • Number the steps of any procedure or implementation sequence. Don't use plain bullets for steps.
  • The number must be visible to the reader, not only present as an id or produced by a CSS counter that a copy and paste would drop.
<h2 id="numbers">3. Section and step numbers</h2>
<h3>3.1 Headings</h3>

4. Dark mode and the toggle

  • The page opens in dark mode.
  • A toggle at the top of the page switches to light mode and back.
  • Colours are CSS variables, so the toggle only swaps one set for the other.
:root                     { --bg: #12161c; --fg: #e3e8ef; }
:root[data-theme="light"] { --bg: #ffffff; --fg: #1c2430; }
button.addEventListener('click', () => {
  const root = document.documentElement;
  if (root.dataset.theme === 'light') delete root.dataset.theme;
  else root.dataset.theme = 'light';
});

5. Demos and diagrams

  • JavaScript, CSS or SVG demos, animations and diagrams go in when the user asks for them.
  • They are written into the document itself.

6. Wide demos

Examples and demos must stay readable. A demo squeezed into the text column ends up with small labels, scaled-down SVGs or a cramped layout.

6.1 The rule

  • Prose stays in the normal reading column.
  • When an example or demo needs more room, that one block breaks out into a wide landscape format.
  • The normal column returns straight after the block.
  • Only the blocks that need the width go wide. Don't widen the whole page.
  • The goal is to preserve text and element size. Give the demo more width; don't scale it down to fit.
  • On a small screen the demo stays wide. It does not shrink to the screen. The reader scrolls it sideways.
  • While a wide block is on screen, the table of contents is hidden, so the block can use the space it occupies. It comes back once the block has scrolled away.

6.2 How

Mark the block with a class. It grows left over the space of the table of contents and right to the edge of the layout. An inner element carries the width the demo needs.

<p>Text in the normal column.</p>

<figure class="doc-wide">
  <div class="doc-wide-in">
    <!-- wide demo / example -->
  </div>
</figure>

<p>Back in the normal column.</p>
.doc-layout      { --toc-w: 220px; --toc-gap: 44px;
                   grid-template-columns: var(--toc-w) minmax(0, 1fr); gap: var(--toc-gap); }
main > *         { max-width: 780px; }                   /* the reading column */
main > .doc-wide { max-width: none; overflow-x: auto;    /* the block leaves it… */
                   margin-left: calc(-1 * (var(--toc-w) + var(--toc-gap))); }  /* …and takes the contents' space */
.doc-wide-in     { min-width: 1100px; }                  /* as wide as the demo needs */

nav.doc-toc           { transition: opacity .2s, visibility .2s; }
nav.doc-toc.is-hidden { opacity: 0; visibility: hidden; }
const toc = document.querySelector('nav.doc-toc');
const onScreen = new Set();
const io = new IntersectionObserver((entries) => {
  entries.forEach((e) => { if (e.isIntersecting) onScreen.add(e.target); else onScreen.delete(e.target); });
  toc.classList.toggle('is-hidden', onScreen.size > 0);
});
document.querySelectorAll('.doc-wide').forEach((el) => io.observe(el));

Where the table of contents is not at the side (a narrow screen, where it sits above the text), the block has no left margin and the contents are not hidden.

6.3 Things to check

  • Table of contents. The wide block must never sit on top of visible contents. They are hidden for as long as any part of a wide block is on screen.
  • Clipping. No ancestor of the block may have overflow: hidden or a max-width that clips it.
  • Small screens. The demo keeps its width and scrolls sideways inside its own block. The text around it does not move.
  • Fixed sizes inside. Set font sizes and control sizes in the demo in px or rem, so the extra width goes to layout and nothing is scaled up or down. For an SVG, widen the viewBox to suit the landscape shape; don't stretch a narrow one.
  • Class name. Prefix it (doc-wide) so it can't collide with a global rule such as .wide.
